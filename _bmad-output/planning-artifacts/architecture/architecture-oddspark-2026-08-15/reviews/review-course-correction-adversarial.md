# Adversarial Review — Course-Corrected Architecture Spine

## Verdict

**Not yet safe for independently built downstream units.** The correction makes the major policy choices explicit, but it still describes several shared identities, mutable records, and failure transitions only in prose. The following counterexamples construct two implementations that obey every AD literally and nevertheless disagree at runtime. These are contract holes, not stylistic preferences.

## Findings

- **The pipeline port rule and the Gate contract permit incompatible input envelopes.** Unit A implements the stated pipes-and-filters rule literally: each stage consumes only the previous stage's value, so `Generate` returns `{candidate, evidence, grounding_report, rubric_version, candidate_ref}` for `Gate`. Unit B implements AD-5 literally and makes `Generate` return only the typed Brief, while `Gate` closes over Evidence, grounding, and rubric state held by the orchestrator because AD-2 says those values are sent to the judge. Both obey AD-2, AD-5, and the single-orchestrator rule, but their `Generate -> Gate` port types cannot compose and Unit B can accidentally judge state from a different attempt. Define one normative immutable `GateInput` envelope and require every field to travel through that port rather than through closures or side channels.

- **The Evidence Bundle union has no common discriminator or closed schema.** Unit A emits website evidence as `{mode:"domain", vertical, clarity, capabilities, channels, observation, scanned_urls}` so downstream code can discriminate it from local evidence. Unit B emits exactly the website object printed in AD-4, which has no `mode`, and infers website mode from the presence of `observation`; it emits the local object with `mode:"local"`. Both follow AD-4 literally, yet a validator written by A rejects B's website bundle and a consumer written by B can misclassify an incomplete website bundle as local. The undefined types of `clarity`, `capabilities`, `channels`, `observation`, `scanned_urls`, and `capability_bundle` add further legal divergence. Publish a closed, versioned discriminated-union schema with required fields, enum values, element types, URL representation, and unknown-field policy.

- **“Single-owner grounding” does not prevent evidence/report mutation or cross-attempt mixups.** Unit A returns a mutable Evidence object, then Generate annotates `capabilities` while producing the Candidate; Gate validates against the resulting object. Unit B snapshots Evidence before Generate and produces the grounding report against that snapshot. Both can claim grounding is checked once by the Brief-schema stage, but the same candidate can receive different grounding outcomes. Worse, AD-2 binds only `candidate_ref`, not the Evidence Bundle, grounding report, rubric, or mode, so an orchestrator can legally pair a candidate with a stale report from the prior retry. Require immutable attempt-scoped inputs and bind a canonical hash covering Candidate, Evidence, grounding report, mode, and rubric version into both the judge request and retained verdict.

- **`candidate_ref` has no normative construction, scope, or source of truth.** Unit A defines it as a UUID allocated before generation; Unit B defines it as a hash of canonical Candidate JSON; Unit C uses the committed Brief id because the naming convention already defines ids. Each is immutable and can be echoed exactly, satisfying AD-2, but adapters, evidence verifiers, and retry orchestration cannot compare them. UUID binding also permits the Candidate to mutate after allocation, while a hash implementation does not. Specify the reference algorithm, canonical serialization, version/domain separator, allocation point, retry uniqueness, and whether it binds only Candidate bytes or the full evaluation context.

- **The adapter boundary permits two incompatible meanings of provider-echoed binding.** Unit A requires the provider/model response itself to contain `candidate_ref` and rejects a missing echo. Unit B receives a provider verdict without a reference, wraps it as `JudgeResult {candidate_ref: request.candidate_ref, verdict}` in the provider client, and argues that the frozen adapter merely adds validated wrapper metadata while mapping the inner verdict losslessly. AD-2 does not say whether adapter-created outer metadata counts as an echo. Both yield 100% “binding” under their own test definition, but B proves only local request bookkeeping. State that the reference must be present in the unmodified provider response covered by provider-wire fidelity, and prohibit the adapter/client from synthesizing or copying it.

- **`CanonicalVerdict` has field types but no semantic consistency invariants.** Unit A accepts `{pass:true}` whenever the top-level flag is true even if Gate 4 or `claims.pass` is false, because all fields are present and no aggregation formula is stated. Unit B recomputes top-level `pass` as the conjunction of exactly one entry for each gate 1–9, `tone.pass`, and `claims.pass`, rejecting disagreement as schema-invalid. Both can say the composite Gate passes only when every semantic check passes—A treats the top-level result as the judge's summary check, B treats children as authoritative—but they disagree on the same response. Define array length/order or uniqueness, closed nested objects, non-empty reason rules, and the exact top-level equivalence invariant; require inconsistent summaries to fail rather than be recomputed.

- **Structural and semantic identity are lists of ingredients, not interoperable identities.** Unit A stores a SHA-256 hash over JSON containing model aliases, prompt source text, adapter source hash, runtime version, and timeout. Unit B stores a human-readable tuple using resolved model ids, compiled prompt bytes, package-lock hash, and platform compatibility date. Both freeze every AD-11 ingredient, but neither can decide whether the other's qualification evidence is current. The ambiguity is especially acute for “runtime,” “request parameters,” and prompt templates whose whitespace or injected rubric changes. Define a canonical manifest schema and serialization, resolution rules for aliases/defaults, source/build hashes, an identity algorithm, and the exact equality check that production uses.

- **There is no authoritative qualification registry or atomic enablement rule.** Unit A considers a role current when a Wrangler variable names an identity found in a bundled evidence manifest. Unit B reads a KV qualification record and considers the role current when all four story booleans are true. Both honor AD-11, but deployment can combine A's new config with B's old evidence, or observe partially updated structural/semantic/full-pair records. Define the single owner and storage of qualification state, the versioned record joining all required evidence to one exact identity, signature/hash verification, activation transaction, startup/request-time behavior, and fail-closed behavior for absent, corrupt, partial, or stale records.

- **Primary/fallback behavior is undefined despite independently qualified roles.** Unit A invokes fallback after any primary timeout, invalid output, or circuit-open result, consuming the next complete pair. Unit B selects fallback only before a strike when the primary is administratively unavailable; any primary runtime failure serves the house Brief because AD-11 says unavailable roles do so. Both avoid pooling and use qualified configurations, but they produce different call counts, latency, and owner-visible results. Define selection precedence, which failure classes may transition to fallback, whether fallback happens within the same strike or only across strikes, circuit-breaker interaction, and whether a failed primary pair consumes one of the Candidate slots before fallback.

- **The six-call ledger has no normative state machine for reservation and consumption.** Unit A atomically reserves two entries before beginning a generation/judge pair, then marks each consumed immediately before its call. Unit B checks that two entries remain but consumes only generation; if local validation rejects the generated Candidate, it never consumes or releases a judge entry and starts another generation. Both can claim they start only a complete pair and consume every actual model invocation before invocation, yet A allows at most three started pairs while B may make up to six generation calls with zero judges. Define ledger states (`available`, `reserved`, `consumed`, `released`), whether a locally rejected generated Candidate consumes the reserved judge slot, who owns transitions, and invariants that can be asserted after every exit path.

- **`E` and evidence-call ownership are not closed.** Unit A computes `E` from actual evidence calls and uses the remaining-ledger formula after evidence completes. Unit B pre-reserves the maximum evidence allowance, calculates a two-Candidate ceiling, then releases the evidence slot when local priors avoid a call. Both satisfy the formula at the moment they apply it but make different numbers of attempts. A future evidence stage making two calls is also neither forbidden nor assigned a defined Candidate ceiling in the examples. Define whether `E` is planned, reserved, or consumed; its permitted range; when the Candidate ceiling freezes; and how evidence errors/timeouts affect ledger state and fallback.

- **The hard deadline lacks a shared clock and cancellation contract.** Unit A starts `STRIKE_BUDGET_MS` at route entry and includes scan/feed/commit time; Unit B starts it when the first model call begins because AD-9 governs model spend. Unit A subtracts the declared timeout exactly, while Unit B adds an implementation-defined safety margin because the rule says a call must “safely” fit. Both use a hoisted budget and reject calls that cannot fit, but one can fall back before any model work while the other can exceed the 15-second request ceiling. Neither AD says whether timed-out provider work must be aborted or may continue billing after the response. Define the monotonic start point, phases included, per-role allocations, fixed reserve margin, abort propagation, and the terminal rule for calls that outlive the response.

- **Provider metering can be compliant yet fail open or double-charge.** Unit A calls `NeuronMeter` before the ledger and provider; if the meter is unavailable it serves the house Brief. Unit B treats metering as a best-effort side effect under the State & mutation convention, consumes the in-memory ledger, invokes the provider, and records usage afterward. A third compliant external-provider adapter may reserve a dollar ceiling rather than measured usage because “approved equivalent” is undefined. All claim to retain/provider-appropriately replace metering, but only A enforces a hard spend gate. Define a provider-neutral preauthorization/commit/refund interface, ordering relative to ledger consumption, idempotency key, timeout/error behavior, retry behavior, unit/currency conversion, and whether meter failure categorically forbids the provider call.

- **The PII lifecycle does not say what is discarded or which representations are covered.** Unit A redacts detected spans from canonical scan text but preserves the rest of the observation, URL, and scan diagnostics. Unit B discards the whole response containing detected PII but retains `scanned_urls`; Unit C keeps raw HTML in exception/platform logs because AD-4 restricts only persistence and model input. Each can say PII exists only in the ephemeral scan buffer and is discarded before Evidence persistence, yet their Evidence, grounding behavior, and operational exposure differ. Define the ephemeral buffer boundary and lifetime, redaction-versus-document rejection, treatment of URLs/metadata/images/errors/logs/caches, zeroization expectations, and whether the personal-name policy runs before any text becomes Evidence.

- **Grounded claim ownership is asserted without a normative claim/provenance representation.** Unit A scans every free-text Brief field for numbers and business nouns, then stores offsets into canonical evidence. Unit B trusts the generator-provided `grounded_numbers[]` list and validates only those strings, while treating “business-specific claim” as a semantic-judge concern. Both can argue that every identified claim traces to the bundle, but B can miss an unlisted fabricated number and A can reject harmless dates or step counts. `grounded_numbers[]` contains values, not field paths or evidence citations, so repeated values cannot be attributed deterministically. Define a machine-readable grounding report schema with Candidate field paths/spans, evidence source ids/spans, claim classes, number exemptions, complete-coverage rules, and the sole component allowed to construct it.

- **Mode downgrade and house fallback leave cache ownership ambiguous.** For a submitted domain that fails the evidence threshold, Unit A produces a `mode:"local"` Brief but commits it under the domain `pw:` claim because AD-7 says per `(round, domain)` and the house Brief commits like any artifact. Unit B commits the same local Brief under the window `w:` pin because `mode` is the sole renderer authority and the artifact is Coherent Local Mode. Both satisfy AD-3, AD-4, AD-5, and AD-7, but subsequent domain and non-domain visitors see different cache convergence, permalink eligibility, notices, and fallback counts. Define a request-mode/effective-mode/cache-key matrix, including threshold downgrade, generation exhaustion, unqualified roles, committed house Brief reuse, and whether `notice` is required for each transition.

- **House Briefs bypass the qualification rules with no executable validity lifecycle.** Unit A treats “gate-passing by construction” as editorial approval and serves the compiled catalog without running local checks. Unit B runs the current AD-4/AD-5 local checks on every house Brief but skips the semantic judge. Both comply with the explicit house exception in AD-1 and consume no model calls, yet a schema/rubric/personal-name-policy change can make A serve a now-invalid artifact while B falls into an unspecified fallback-of-last-resort. Define a build/startup validation gate, the exact identities against which each house Brief was approved, invalidation rules for schema/rubric/policy changes, and terminal behavior when no current house Brief validates.

- **Committed artifact version rejection has no owner or recovery behavior.** Unit A's new renderer rejects an older pinned Spark and regenerates/commits a new Brief; Unit B returns the house Brief without mutating the existing pin because AD-7 promises later requests serve the committed artifact. Both honor “old renderers reject newer Brief versions” and avoid misrendering, but they disagree on whether cache-first reproducibility or availability wins during mixed-version rollout. The commit envelope and provenance fields are also not defined, so SparkCoordinator and renderers can validate different shapes. Specify the persisted envelope schema, supported version matrix, validation owner, read-failure response, pin replacement/migration authority, and behavior in both old-code/new-data and new-code/old-data directions.

- **Infrastructure failure has contradictory but individually plausible terminal behavior.** The Data & formats convention says infra/feed errors become `502` JSON, while AD-3 says grounding/infra failure invalidating a Candidate serves the house Brief and AD-9 says unavailable configurations serve the house Brief. Unit A maps scan/feed/COORD failures to `502`; Unit B catches every such failure inside the orchestrator and returns a house Brief. Each can cite a direct rule. Define a closed failure taxonomy and a single transition table assigning each failure to retry, fallback, cached response, or HTTP error, including whether commit failure may render an uncommitted Brief and whether analytics/meter failures alter the result.

## Required closure

Before Story 1.2 evidence-v2 or downstream pipeline implementation is treated as architecture-conformant, the spine needs normative, versioned contracts for: the attempt envelope and Evidence union; grounding report and full-context binding; candidate and qualification identities; qualification registry/activation; role fallback; ledger/deadline/meter state machines; PII lifecycle; cache/mode/fallback matrix; house-Brief validity; persisted artifact envelope; and the failure taxonomy. Without those contracts, tests written by one unit can certify behavior that another equally compliant unit rejects.

This review does not authorize implementation, provider selection, metered calls, deployment, commit, or push.
